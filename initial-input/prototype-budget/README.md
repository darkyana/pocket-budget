# 口袋账房（原型）产品说明

> 配套原型：`app.html`（本目录，手机浏览器直接打开）。
> 性质：**一次性原型**，用于验证"当下的钱"这个产品方向的核心假设；尚未进入正式产品重写流程（#10 功能树之外）。
> 状态记录：全部数据存浏览器 localStorage，可在流水页清空、设置页恢复出厂。不接触任何真实账本文件。

## 1. 它回答的问题

正式产品（#10 重写线）非常适合理账：把账搞清楚、对平、敲定。但记账之后，用户面对的是**当下的消费决策**——今天还能花多少、这笔该不该买、这个月的钱都去哪了。本原型回答：

> 一个手机上的日常工具，如何既生成可靠的凭证记录，又在记录时给足引导，帮助用户按自己的消费模式做花销决策？

## 2. 核心模型：三种锚

不同消费的管理方式不同，"预算"不是一种东西。所有经济事件按记录入口天然带上自己的锚：

| 锚 | 管理对象 | 今天的答案 | 典型例子 |
|---|---|---|---|
| **节律**（rhythm） | 消费节奏 | 按今天的日子类型，各类别期望花多少，实际多少 | 三餐、交通、咖啡 |
| **预算池**（budget pool） | 可花的池子 | 各池子还剩多少（月预算摊到周） | 购物、学习、娱乐 |
| **义务**（commitment） | 月内必付的固定项 | 哪些还没付（二元状态，不占任何额度） | 家政服务、宠物粮、物业费 |

另有第四种记录类型：

- **走账**（transfer）：钱在账户间移动（现金→卡、卡→卡、投资划转），不是消费，不占任何额度，只是流水里的一条事实。账户名自由输入、自动记忆。

关键设计裁定（原型期间已验证的方向）：

1. **日型决定节律期望**。同是"三餐"，周末日期望 ¥500、工作日期望 ¥50。评判今天花多花少，必须先知道今天是什么日子。日型方案在设置里按日型各存一套，可增删改。
2. **预算池主信号是"还能花"**。首页池子按剩余额降序排列；**超支的池子从首页退场**——当天视图不做裁判，只回答"现在还能在哪花钱"。超支的复盘信号归每周/阶段性的对齐动作，不占用日常注意力。
3. **义务是状态不是流量**。付了和没付两个状态，常驻页面但视觉最弱（无底色小票样式）；它不影响每天能花多少。
4. **记录入口即分类**。从节律卡片发起 = 记一笔该类消费；从池子发起 = 该池的收支；从义务发起 = 切换付/未付；走账按钮 = 账户间移动。"记凭证时有足够引导性"由入口结构保证，用户不需要事后归类。
5. **"还能花"优先于"已花多少"**。所有金额的主数字都是剩余/超出，已花是次要小字。

## 3. 页面结构

### 今日（默认页，overview + 记一笔入口）

- **节律**：标题行纯文字数字（还能花 X / 期望 Y · 已花 Z）；下方小卡片 2×2 网格，超过 4 类左右滑动翻页；卡片主数字为剩余（超支显红"超"），点卡片记一笔。
- **预算池**：只列还能花的池子，按剩余降序；每池显示本周剩余（主）、月累计与按当前节奏的**月底推算**；点池记一笔收支（支出/回血）。
- **义务 · 本月**：小票式列表，已付划线、未付金额橙色加粗；点一条切换状态。
- **记一笔走账**：页面底部浅色按钮。

### 流水

全部经济事件时间倒序一览（类型 · 名称 · 备注 · 时间 · 金额）。两个动作：

- **导出凭证文件**：下载 JSON（含导出时间戳 + 全部设置与事件）。这是本工具与账本正本的接口雏形——格式目前为示意，待真实使用数据回来后再定稿。
- **清空全部记录**：只清事件，设置保留。

### 设置

三个分栏，全部支持新增/修改/删除：

- **节律方案**：切换今天的日型；编辑各类别单日期望；新增/删除类别。
- **义务**：月度固定项的名称与金额。
- **预算池**：名称、月预算、每周额度。
- 恢复出厂：清空一切重新开始。

## 4. 边界（它刻意不做的）

- **不做账户余额台账**：走账只记"从 A 到 B"的动作，不在账户上累加余额。若使用中出现"想看现金还剩多少"的需求，再考虑引入账户维度。
- **不做报表与对账**：那是正式产品（M9+）的领地；本工具的输出是凭证文件，理账能力复用正式产品。
- **不做多人/多端**：单机单用，localStorage 即可。
- **不碰真实账本**：读写仅限本机浏览器存储与用户手动导出的文件。

## 5. 待真实使用验证的开放问题

1. 节律卡片的渐近变色（余量 <20% 黄）是信号还是噪音；
2. 预算池"月底推算"会不会制造焦虑、盖过"本周剩余"主信号；
3. 三种入口 + 走账是否覆盖日常全部记录动作；出现第五种锚怎么办（预期：用着用着会冒出来，届时新增，不预设）;
4. 凭证文件的定稿格式：要能被正式产品无损接收（对齐 #10 架构铁律的全量无损精神）；
5. 义务的月度周期重置时机（自然月？手动？）。

## 6. 归档与后续

- 原型按纪律视为一次性代码；三方案对比版保留在 `variants.html` 供回溯（A/B/C/D 原始方案探索过程）。
- 若决定进入正式产品：走 grill → spec → ticket 流程，与 #10 排期衔接（预估与 M1 凭证导入、"开始记新账"节点强相关——本工具的凭证格式与 M1 的导入格式应一并设计）。
