# 第三方对接指南：生成可导入的凭证（voucher）文件

> 面向想在自家 app 里生成凭证文件、供本 app「增加凭证」功能导入的第三方开发者。
> 依据实现：`app/src/importVouchers.ts`（缝 J，spec #53 / Issue #54）、`app/src/voucherImportPage.ts`。schema 版本：**voucher 1.0**（2026-10）。

## 一分钟了解

本 app 的「增加凭证」入口（全部账目页头部按钮）接收**多个 JSON 文件**（`.json`），每个文件是一张「凭证」——一组交易行的列表。导入后每行生成一笔 `draft`（草案）分录，进入后续的消费/收入归类流程。

第三方 app 要做的事只有一件：**按下面的格式导出一个 JSON 文件**，用户手动在导入入口选中它即可。没有 API、没有网络调用，纯文件交换。

## 文件格式

- 一个 UTF-8 编码的 JSON 文本文件，扩展名 `.json`。
- 顶层必须是一个 JSON **对象**（不能是数组）。
- 必填字段两个：`voucher_schema_version` 和 `rows`。

```json
{
  "voucher_schema_version": "1.0",
  "meta": { "source": "某 app 导出 2026-10" },
  "rows": [
    { "date": "2026-10-02", "account": "1002", "amount": -18.50, "description": "午餐 — 沙县" },
    { "date": "2026-10-01", "account": "1001", "amount": 25375.88, "description": "工资 — 上海微创" }
  ]
}
```

### 顶层字段

| 字段 | 必填 | 要求 |
|---|---|---|
| `voucher_schema_version` | 是 | 必须是字符串 `"1.0"`，任何其他值整文件拒载 |
| `rows` | 是 | 数组，至少 1 行；空数组拒载 |
| `meta` | 否 | 对象。导入时仅保留不解析，可放任意导出方元信息 |
| 其他字段 | 否 | **未知字段一律忽略、不拒载**——可放心携带额外信息，将来版本可原样重读 |

### 每行（rows 数组元素）字段

| 字段 | 类型 | 要求 |
|---|---|---|
| `date` | string | `YYYY-MM-DD`，且必须是真实日历日（`2026-02-30` 会拒） |
| `account` | string | 非空字符串。钱所在账户，详见下节「account 怎么填」 |
| `amount` | number | 带符号 JSON 数字（不能是字符串），有限数且 **≠ 0**。**负数 = 该账户支出/扣款；正数 = 该账户收入/入账** |
| `description` | string | 非空字符串。建议带商户/用途信息，便于后续归类 |

行内未知字段（如 `category`、`note`、交易流水号）同样忽略不拒载——**建议把你们 app 的原始交易 ID 放进额外字段**（如 `"ref_id": "..."`），账面上不生效，但文件重读/排查时有据可查。

## account 怎么填

`account` 指的是**钱所在的账户**（银行卡/零钱/现金/信用卡等），不是消费类别。类别由导入后的归类流程处理，凭证只管「哪个账户、进出多少」。

导入时按以下顺序落点，**填得越准，用户越不用手动指认**：

1. **科目码直通**：填科目表中的码，如 `"1001"`、`"2001"` → 直接命中，无需用户操作（推荐）。
2. **精确科目名**：填与科目表完全一致的名称，如 `"微信零钱"` → 唯一命中即自动解析；命中多个同名科目则要求指认。
3. **简称/别名**：填不了精确名称时，随便填个可辨认的名字（如 `"微信"`），用户导入时会在弹层里通过下拉框指认到具体账户。**指认一次对本次全部文件生效，但不会持久化**——下次导入同名的还要再指认。

用户可指认的范围只有**银行/账户类科目**（1xxx 资产段，但 12xx 往来段除外；2xxx 负债段）。所以：

- 填 `1001`~`1006`、`2001`、`2002` 这类码最省事；
- **不要**把 account 填成消费类别（如「餐饮」）、往来对象或投资标的——这些科目不在指认范围内，会整批拒载。

## amount 符号语义

导入按符号自动定向生成草案分录：

- `amount < 0`（支出）：借「5000 待分类消费」/ 贷该账户
- `amount > 0`（收入）：借该账户 / 贷「4000 待分类收入」

注意：**信用卡还款、转账这类资金在两个账户间移动的交易，本格式无法表达**（一行只能描述一个账户的净变动）。两张卡各记一行会出现重复口径，建议此类交易不要写入凭证文件。

## 拒载规则（重要）

**文件级原子**：一个文件里任何一行任何已知字段非法，**整个文件一个分录都不入账**；但多个文件之间互不影响（坏文件不阻断好文件）。错误信息会精确指到文件名与行号。

常见拒载原因：

| 错误 | 原因 |
|---|---|
| 不是合法 JSON | 文件不是有效 JSON 文本 |
| 顶层必须是 JSON 对象 | 顶层写成了数组 |
| voucher_schema_version 必须为 "1.0" | 版本号缺失或不对 |
| 缺少 rows 数组 | 忘了 `rows` |
| 日期非法 | 格式不是 `YYYY-MM-DD`，或不是真实日历日 |
| 金额为 0 / 金额非法 | `amount` 是字符串、非有限数（`NaN`/`Infinity`）或 0 |
| 账户非法 | `account` 空字符串或非字符串 |
| 描述非法 | `description` 空字符串或非字符串 |
| 无法落点 / 命中多个同名科目 | account 既不是科目码、不是唯一科目名，用户又没指认 |

## 其他须知

- **无查重**：导入是纯加法，同一文件导两次会得到两批草案、两套分录 ID（重叠检测是后续 M2 的能力）。第三方 app 应自己避免重复导出（例如记录「已导出」标记），只导增量。
- **不修改既有数据**：导入只新增草案，绝不改动用户已有的分录。
- **文件名会显示在错误信息里**，建议用有意义的名字（如 `wechat-2026-10.json`）。
- **文件大小**：没有硬限制，但指认弹层会列出文件中所有不同的 account 名，建议按月/按账户拆分文件，单文件别太大。
- 完整最小示例见仓库 `app/fixtures/voucher-template.json`。
