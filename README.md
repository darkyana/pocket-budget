# 口袋账房（pocket-budget）

> 当下的钱：一个回答「今天还能花多少、这笔该不该买」的手机 PWA。
> 数据全部留在你自己的浏览器里——无账号、无服务器、无上报。

线上地址：<https://darkyana.github.io/pocket-budget/>（手机 Safari 打开 → 分享 → 添加到主屏幕，即可像原生 App 一样离线使用）

## 它解决什么问题

记账工具大多擅长「理账」：把账搞清楚、对平、敲定。但记账之后，人面对的是**当下的消费决策**——今天还能花多少、这笔该不该买、这个月的钱都去哪了。

口袋账房只回答这一类问题。对账、报表、多端同步不在它的范围（导出的凭证文件是未来与理账工具对接的接口）。

## 核心模型：三种锚 + 走账

「预算」不是一种东西。不同性质的消费用不同的方式管理，所有经济事件按记录入口天然带上自己的锚：

| 锚 | 管理对象 | 回答的问题 |
|---|---|---|
| **节律** | 消费节奏 | 按今天的日子类型，各类别期望花多少、实际多少（工作日三餐 ¥50，周末 ¥500） |
| **预算池** | 可花的池子 | 各池子还剩多少（月预算摊到周；超支的池子从首页退场，不当裁判） |
| **义务** | 固定要付的钱 | 付了没（每月 / 每年两种周期；是状态不是流量，不占任何额度） |
| **走账** | 账户间的移动 | 现金→卡、卡→投资划转的事实记录，不是消费 |

几条贯穿的设计立场：日型决定节律期望；入口即分类（从哪发起就记哪种锚，不需要事后归类）；「还能花」优先于「已花多少」。

## 功能

- **今日**：节律卡片（点卡片记一笔）、预算池（点池记收支，回血计入净支出）、义务小票（点条切换付/未付）、走账入口
- **流水**：全部事件按天分组；点任意一笔可编辑（金额/账户/备注/日期）或删除；节律 ↔ 预算池可互转改类（先批量记、回头分类）；按账户 / 日期筛选对账；收入支出分色
- **补记与连记**：记账时可指定任意日期（自动归入那天的额度与周期）；「再记一笔」连续录入不关弹层
- **凭证**：一键导出全量 JSON（设置 + 全部事件），导入整包恢复——换设备即搬家
- **PWA**：可安装到主屏幕，Service Worker 离线可用

## 架构

事件溯源的极简实现，三层单向依赖：

```
src/
  core/      纯领域层：types / time / derive / seed
             （零依赖纯函数；事件是唯一事实源，所有视图数字渲染时推导，永不落库）
  storage/   IndexedDB 持久化 + schemaVersion 迁移钩子 + 凭证导入导出
  app/       React UI：三页 + 弹层组件（ zustand 状态容器 ）
```

- **事件是唯一事实源**：今日已花、周剩余、月底推算、义务状态全部由时间戳实时推导，跨天/跨周/跨月的翻转不需要任何定时重置
- **结构演进有退路**：schemaVersion + 就地迁移（v1→v2 已在生产数据上跑过一次），两周实验中途改结构不丢数据
- 钱的计算被 24 个单元测试盯着（周边界、跨年、推算、净支出）

## 本地开发

```bash
npm install
npm run dev        # 开发服务器
npm test           # 单元测试
npm run build      # 产物构建（tsc + vite）
```

技术栈：React 19 · TypeScript · zustand · idb · Vite · vite-plugin-pwa · lucide-react · vitest

## 数据与隐私

- 所有数据仅存于浏览器 IndexedDB，并请求了持久化存储
- 没有账号体系、没有云端、没有任何网络上报；仓库里没有任何真实数据
- 恢复出厂 / 清空记录都在应用内自己控制

## 状态与来路

两周个人实验版（会随真实使用持续迭代）。由一个一次性原型演化而来——原型与三方案对比存档在 [`initial-input/`](initial-input/prototype-budget/README.md)，产品裁定与开放问题的原始记录也在那里。按原型纪律：这是验证方向的工具，不是正式产品；若方向验证成立，走正式流程重写。
